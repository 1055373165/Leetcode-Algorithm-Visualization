# LeetCode 15. 三数之和 —— 排序降维、对撞排除与去重不变量

---

## 问题本质

题目要求在一个整数数组中找出所有和为零的不重复三元组。表面上是组合搜索——从 n 个数中选 3 个使得和为零，枚举空间是 C(n,3) = O(n³)。但这道题真正在解决的问题是：**如何在"高效搜索"和"原生去重"这两件事上同时找到最优策略，而不是先搜索再去重。**

关键结构特征在于：三数之和 `a + b + c = 0` 可以改写为 `b + c = -a`。固定一个数之后，剩下的部分退化为 Two Sum。而 Two Sum 在有序数组上可以用对撞双指针 O(n) 解决。这个**递归降维**的视角——k-Sum 降为 (k-1)-Sum——是整道题的结构性入口。

## 为什么应该往排序 + 双指针方向想

`n ≤ 3000`，O(n²) ≈ 9×10⁶ 可以接受，O(n³) ≈ 2.7×10¹⁰ 会超时。目标复杂度是 O(n²)。

题目有两个并行的挑战：一是找到所有和为零的三元组，二是结果不能有重复。如果用哈希表做 Two Sum 式的查找，搜索本身可以做到 O(n²)，但去重变得极其棘手——你需要处理"同一个元素被用了两次"、"三元组的排列顺序不同但本质相同"等一堆边界情况。而排序天然解决了去重问题：相同的数字挨在一起，只需 `if nums[i] == nums[i-1] { continue }` 就能跳过重复。排序的 O(n log n) 被 O(n²) 支配，相当于免费获得了去重能力。

所以"排序 + 双指针"是唯一一种能同时优化搜索效率和去重成本的方案。这不是两个独立优化的叠加，而是一个设计选择同时解决了两个问题。

## 暴力思路与它的瓶颈

三重循环枚举所有 `(i, j, k)` 组合，对每个和为零的三元组排序后放入 Set 去重。时间 O(n³)，在 `n = 3000` 时完全不可行。

瓶颈有两层。第一层是**搜索**：固定 `i` 和 `j` 后，找满足条件的 `k` 是线性扫描，没有利用任何结构。第二层是**去重**：搜索产生重复后再用 Set 过滤，等于先制造问题再解决问题。这两个瓶颈共同指向"排序"这个优化方向——排序既让搜索可以用双指针加速（消除第一层瓶颈），又让去重可以用跳过策略在线完成（消除第二层瓶颈）。

## 关键思维转折

**转折一：降维。** 三数之和 = 固定一个数 + 两数之和。这不只是数学等式变换，而是一种通用的递归分解：任何 k-Sum 问题都可以通过"枚举一个 + 解 (k-1)-Sum"来降维。认识到这一点，就把一个看似需要全新算法的问题，归约到了一个已知的子问题上。

**转折二：排序不只是为了搜索，更是为了去重。** 很多人知道"排序后可以用双指针"，但忽略了排序对去重的价值。在无序数组中判断"这个三元组是否已经被找过"需要 O(1) 的 Set 查找 + O(k) 的排序开销。排序后只需要"和前一个数比较"这个 O(1) 操作就能完成去重，且是在搜索过程中原生完成的，不需要事后处理。

**转折三：去重的两层结构。** 这是最容易写错的地方。去重发生在两个层面：外层枚举 `nums[i]` 时，如果 `nums[i] == nums[i-1]`，说明以这个值作为第一个数的所有三元组已经在上一轮被穷举过了，必须跳过。内层找到一组解后，`left` 和 `right` 各自跳过与当前值相同的元素，避免以相同的 `(b, c)` 对再次命中。漏掉外层去重会产生重复三元组，漏掉内层去重会在某些输入上死循环。

**卡点预警**：如果你没见过双指针去重的模式，你写到"找到一组解之后怎么办"这一步会卡住——你的本能反应可能是 `break` 或者只移动一个指针，然后发现有些解被遗漏了或者重复了。正确的做法是：记录解 → left 跳过重复 → right 跳过重复 → left++ → right-- → 继续循环。

## 正确性论证

**不会漏解**：外层循环枚举了所有不同的 `nums[i]` 值作为第一个数（去重只跳过重复值，每个值的第一次出现不会被跳过）。对于每个 `nums[i]`，内层双指针从 `[i+1, n-1]` 的两端出发，覆盖了所有可能的 `(left, right)` 配对。双指针的正确性来自有序性：当 `sum < target` 时 `left++` 排除了所有以当前 `left` 为左端点且 `right` 更小的配对（它们的和只会更小），当 `sum > target` 时 `right--` 排除了所有以当前 `right` 为右端点且 `left` 更大的配对（它们的和只会更大）。每次排除的是一整行或一整列候选，不会跳过最优解所在的配对。

**不会重复**：外层去重保证每个值只作为第一个数被使用一次。内层去重保证每对 `(nums[left], nums[right])` 只被记录一次。两层去重叠加，确保最终结果中的三元组在**值**的层面上没有重复。

**结果有序性**：因为数组已排序，输出的每个三元组 `[nums[i], nums[left], nums[right]]` 天然满足 `nums[i] ≤ nums[left] ≤ nums[right]`，无需额外排序。

## 复杂度的真实来源

**时间 O(n²)**：排序 O(n log n)。外层循环最多 n-2 次。每次内层双指针：`left` 从 `i+1` 开始，`right` 从 `n-1` 开始，两端向中间收缩，合计最多走 `n - i - 2` 步。所有内层步数之和为 Σ(n-i-2) ≈ n² / 2 = O(n²)。去重跳过操作不增加额外复杂度——跳过的步数已经包含在指针移动的总步数中。排序的 O(n log n) 被 O(n²) 支配。

**空间 O(log n)**：排序的栈空间（Go 的 `sort.Ints` 使用 pdqsort）。没有使用哈希表或其他辅助结构。结果切片不计入辅助空间。

## 思路验证

用 `nums = [-1, 0, 1, 2, -1, -4]`，排序后 `[-4, -1, -1, 0, 1, 2]`。

**i=0，nums[i]=-4，target=4**：left=1(-1)，right=5(2)，sum=-1+2=1 < 4，left 一直右移但始终不可能凑到 4。无解，符合预期——-4 太小了，剩余元素之和最大才 -1+2=1。

**i=1，nums[i]=-1，target=1**：这是关键轮次。left=2(-1)，right=5(2)，sum=-1+2=1 == target → 记录 `[-1,-1,2]`。然后 left 跳过重复的 -1（此时 left 已在位置 2，没有更多重复），right 跳过重复的 2，left++→3，right--→4。现在 left=3(0)，right=4(1)，sum=0+1=1 == target → 记录 `[-1,0,1]`。left++→4，right--→3，left ≥ right，内层结束。

**i=2，nums[i]=-1，与 nums[1] 相同 → 外层去重跳过。** 这一步至关重要：如果不跳过，会再次找到 `[-1,0,1]`，产生重复。

**i=3，nums[i]=0，target=0**：left=4(1)，right=5(2)，sum=3 > 0 → right--，left ≥ right，无解。

**i=4，nums[i]=1 > 0**：三个非负数之和不可能为零，可以剪枝跳出（不剪枝也可以，只是多走两步空循环）。

最终结果：`[[-1,-1,2], [-1,0,1]]` ✅

去重边界用例 `nums = [0,0,0,0]`：排序后 `[0,0,0,0]`。i=0 时 target=0，left=1，right=3，sum=0 == target → 记录 `[0,0,0]`，然后 left 跳过重复到 2，right 跳过重复到 2，left ≥ right 结束。i=1 时 nums[1]==nums[0] 跳过。i=2 同理。结果只有一个 `[0,0,0]` ✅

## 代码（Golang）

```go
func threeSum(nums []int) [][]int {
	sort.Ints(nums)
	n := len(nums)
	var result [][]int

	for i := 0; i < n-2; i++ {
		if nums[i] > 0 {
			break // 最小的数已经 > 0，不可能凑出零
		}
		if i > 0 && nums[i] == nums[i-1] {
			continue // 外层去重
		}

		left, right := i+1, n-1
		target := -nums[i]

		for left < right {
			sum := nums[left] + nums[right]
			if sum < target {
				left++
			} else if sum > target {
				right--
			} else {
				result = append(result, []int{nums[i], nums[left], nums[right]})
				// 内层去重：跳到最后一个相同值，再 +1/-1 进入新值
				for left < right && nums[left] == nums[left+1] {
					left++
				}
				for left < right && nums[right] == nums[right-1] {
					right--
				}
				left++
				right--
			}
		}
	}

	return result
}
```

## 易错点

| 场景 | 陷阱 | 正确处理 |
|------|------|----------|
| 外层去重方向 | 写成 `nums[i] == nums[i+1]` | 应比较 `nums[i-1]`；比较后一个会跳过该值的**首次**使用，导致漏解 |
| 内层去重后漏移 | 跳过重复值后没有 `left++; right--` | 跳过循环只走到最后一个重复值，还需再移一步才能到新值 |
| 单侧去重 | 只跳了 left 忘跳 right，或反过来 | 两侧都必须跳，否则产生重复三元组 |
| 循环条件 | 内层去重循环忘加 `left < right` 守卫 | 没有守卫可能导致越界 |
| 外层范围 | `i < n` 而非 `i < n-2` | 需要给 left 和 right 留位置 |
| `[0,0,0,0]` | 外层去重可能把 i=0 也跳过 | 条件是 `i > 0 &&`，确保首次使用不被跳 |

## 可迁移方法论

**排序 + 对撞双指针 + 在线去重** 是一个组合范式，适用于所有 k-Sum 变体：

- **16. 最接近的三数之和**：框架不变，判断条件从 `== 0` 改为用差的绝对值更新最优，不需要去重。
- **18. 四数之和**：外层再包一层枚举，降维到三数之和。复杂度 O(n³)，去重逻辑在每一层都需要。
- **167. 两数之和 II**：三数之和的内层子问题。理解了 167，三数之和就是外面包一层枚举。
- **259. 较小的三数之和**：双指针找到 `sum < target` 时，`right - left` 个配对都满足条件，一次性计数而非逐个记录。

迁移时保留的结构是"排序 → 外层枚举 → 内层对撞"这个三段式，需要修改的是：判定条件（等于/小于/最接近）、结果收集方式（记录三元组/计数/更新最优值）、去重是否需要。

## 进阶实现视角

上面的排序 + 双指针方案在算法层面已经是 O(n²) 最优——无法在渐进复杂度上做得更好（因为最坏情况下合法三元组的数量本身就是 O(n²) 的，比如 `[-n, ..., -1, 0, 1, ..., n]`）。在面试和绝大多数业务场景中，上面的实现已经是最佳平衡。

但如果你在做性能敏感的批处理系统，或者需要在超大规模数据上反复执行类似的多元素求和匹配（例如金融系统中的三方头寸对冲检测），有三个工程层面的优化方向值得了解：

**1. 减少 slice 分配。** 标准实现中每找到一组解就 `append(result, []int{...})`，每次都会分配一个新的 `[]int` 和可能的 `result` 扩容。在高命中率场景下，可以预分配一个足够大的二维切片，或者用一维数组 + 偏移量来模拟二维结构，消除 GC 压力。代价是代码可读性下降、返回值的类型不再是标准的 `[][]int`。

**2. 利用值域收窄搜索范围。** 排序后如果 `nums[i] + nums[i+1] + nums[i+2] > 0`，后续所有 i 都不可能找到解；如果 `nums[i] + nums[n-2] + nums[n-1] < 0`，当前 i 不可能找到解，可以跳过。这两个剪枝在数据分布偏斜时非常有效（比如大量正数或大量负数），但对均匀分布帮助不大。

**3. 计数排序替代比较排序。** 当值域有限（如 `-10⁵ ≤ nums[i] ≤ 10⁵`），可以用计数数组统计每个值的出现次数，然后在值域上直接枚举 `(a, b)`，`c = -a-b`，检查这三个值的计数是否够用。这完全避免了指针移动和去重逻辑——因为你直接在值域空间上工作，每个值只出现一次（出现次数用计数表达）。时间复杂度为 O(V²)，其中 V 是值域宽度。当 n 很大但值域有限时（如 n=10⁶, V=200000），O(V²) = 4×10¹⁰ 反而更慢；但当 n >> V 时（大量重复值），这种方法可以显著加速，因为它的开销与 n 无关，只与不同值的个数有关。

这些优化的共同特点是：不改变渐进复杂度，而是在常数因子、内存分配模式或特定数据分布上做文章。它们适用于"这段代码是热路径，被调用百万次"的场景，而不是"做一道 LeetCode 题"的场景。知道它们的存在，知道它们解决什么问题，知道什么时候应该停在常规最优——这本身就是工程判断力的一部分。
