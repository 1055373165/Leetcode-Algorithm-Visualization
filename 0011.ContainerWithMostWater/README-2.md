# LeetCode 11. 盛最多水的容器 —— 双指针为什么敢跳过？贪心背后的不可能性论证

---

## 问题本质

题目给你一个整数数组 `height`，其中 `height[i]` 代表第 `i` 条垂线的高度。你要选两条线，和 x 轴一起构成一个容器，使得容器盛的水最多。返回最大面积。

表面上这是一个"选两条线"的组合优化问题，但底层结构是：**在 n 个元素中选一对 `(i, j)`，使得 `min(height[i], height[j]) × (j - i)` 最大化。** 这是一个关于"宽度"和"高度"二者博弈的问题——宽度越大容器越宽，但高度受限于较短的那条线。这两个因素的方向是相反的：宽度最大时（两端），高度可能很低；高度最大时（最高的两条线），宽度可能很小。最优解是二者的某种平衡。

这道题最关键的结构特征是：**面积的瓶颈始终由较短的那条线决定。** 这个不对称性是整个双指针策略的出发点。

## 为什么应该往双指针方向想

数据范围 `n ≤ 10⁵`，这意味着 O(n²) 大约 10¹⁰ 次运算，会超时。我们需要一个 O(n) 或 O(n log n) 的方案。

观察目标函数 `min(h[i], h[j]) × (j - i)`：它依赖两个变量的选择，但不是简单的线性组合，而是受限于一个 `min` 操作。`min` 的存在意味着"短板效应"——提升较长的那条线不会带来任何收益，只有提升较短的那条线才可能增大面积。

这种"一个变量受制于另一个变量的约束、且约束方可以被有方向地调整"的结构，非常适合**对撞双指针**（从两端向中间收缩）。因为初始状态下宽度最大，每次收缩都会减少宽度，所以我们必须确保每次收缩有可能带来更高的 `min(h[i], h[j])` 来补偿宽度的损失。

## 暴力思路与它的瓶颈

最朴素的方案是枚举所有 `(i, j)` 对，计算面积并取最大值。O(n²) 的时间在 `n = 10⁵` 时不可接受。

但暴力解法的问题不仅仅是"慢"——更关键的是它没有利用任何数学结构来剪枝。当我们在枚举过程中发现某些配对**不可能**比当前最优解更好时，应该直接跳过它们。问题是：我们能不能找到一条规则，在 O(1) 的时间内排除掉大量不可能的候选对？

## 关键思维转折：移动短板的不可能性论证

双指针的起点是 `left = 0, right = n - 1`，此时宽度最大。然后每一步，我们移动一个指针来收缩窗口。**移动哪个？**

假设 `height[left] ≤ height[right]`——即左边是短板。此时面积 = `height[left] × (right - left)`。

现在考虑：如果我们不移动 `left`，而是把 `right` 向左移动一步，会发生什么？宽度减少了 1，而高度呢？新的 `min(height[left], height[right-1])` 一定 ≤ `height[left]`（因为 `min` 操作的上界就是 `height[left]`，无论 `height[right-1]` 多高都没用）。所以面积一定不会增大——宽度变小了，高度最多不变。

这个推理的结论是：**在 `left` 固定的前提下，把 `right` 从当前位置向左移动到任何位置，得到的面积都不会超过当前值。** 因此，所有 `(left, right-1)`、`(left, right-2)`、...、`(left, left+1)` 这些配对都可以一次性排除。这不是对一个候选的排除，而是对一整行候选的批量排除。

所以我们应该移动短板一侧的指针。移动长板一侧没有排除效果——因为短板不变，`min` 的上界不变，宽度还在减小，所以只会更差或持平。而移动短板一侧虽然宽度也在减小，但至少有可能遇到更高的线来提升 `min` 值，从而有机会获得更大的面积。

**这就是这道题最核心的思维转折：双指针不是在"找更优解"，而是在"排除不可能的解"。每次移动短板，等价于证明了一整列候选对不可能比当前更优，从而安全地跳过它们。**

## 正确性论证

需要证明：双指针过程不会跳过最优解。

设最优解对应的配对是 `(i*, j*)`，其中 `i* < j*`。考虑双指针的执行过程：初始时 `left ≤ i*` 且 `right ≥ j*`。只要 `left` 还没越过 `i*` 或 `right` 还没越过 `j*`，这对组合就还没有被跳过。

当 `left < i*` 时，如果 `left` 是短板，它会被移动，朝 `i*` 靠近。如果 `right` 是短板并被移动呢？此时 `height[right] < height[left]`，而移动 `right` 排除的是所有以 `right` 为右端点、`left`（及更右）为左端点的配对。因为 `right > j*`，`(i*, right)` 确实被排除了——但它被排除是合理的吗？是的，因为 `height[right] < height[left] ≤ height[i*]`（注意 `left ≤ i*`，但这里的推理需要更精细）。

更严格地说：当某个指针被移动时，被排除的所有配对的面积都不超过当前状态下计算出的面积。因此如果最优解的面积严格更大，它对应的配对不会被排除。归纳下去，最优解一定会在某个时刻被 `left` 和 `right` 恰好停在 `i*` 和 `j*` 时被计算到。

## 复杂度的真实来源

**时间 O(n)**：`left` 从 0 开始只增不减，`right` 从 n-1 开始只减不增。两者合计最多走 n-1 步就会相遇。每步只做一次面积计算和一次比较，都是 O(1)。所以总操作次数严格为 n-1。

**空间 O(1)**：只需要 `left`、`right`、`maxArea` 三个变量，不需要任何辅助数据结构。

注意：这个 O(n) 不是均摊的，是每步严格 O(1) 的精确 n-1 步遍历。这比很多"看起来是 O(n) 实际需要均摊分析"的算法要简洁得多。

## 思路验证

用官方示例 `height = [1,8,6,2,5,4,8,3,7]` 手动推演，重点关注**为什么答案 49 不会被跳过**：

```
初始: left=0(h=1), right=8(h=7), 面积=min(1,7)×8=8, maxArea=8
  → h[left]=1 是短板，移动 left

left=1(h=8), right=8(h=7), 面积=min(8,7)×7=49, maxArea=49  ← 最优解在第二步就被捕获
  → h[right]=7 是短板，移动 right

left=1(h=8), right=7(h=3), 面积=min(8,3)×6=18, maxArea=49
  → h[right]=3 是短板，移动 right

left=1(h=8), right=6(h=8), 面积=min(8,8)×5=40, maxArea=49
  → 两边等高，移动任一边都可以（结果不影响正确性）

...后续步骤宽度持续缩小，面积不再超过 49
```

关键观察：第一步 `left=0, h=1` 被移走时，所有以位置 0 为左端点的配对 `(0, 8), (0, 7), ..., (0, 1)` 被一次性排除——因为它们的面积上界都是 `1 × 宽度 ≤ 1 × 8 = 8`，不可能超过后续发现的更大值。这就是双指针的批量排除效应在起作用。

再看一个能暴露理解误区的小用例 `height = [1,2,1]`：

```
left=0(h=1), right=2(h=1), 面积=min(1,1)×2=2, maxArea=2
  → 两边等高，移动 left（或 right 均可）

left=1(h=2), right=2(h=1), 面积=min(2,1)×1=1, maxArea=2
  → 宽度太小，面积反而更小

结果: 2
```

这个例子说明：**最高的线（位置 1，高度 2）不一定出现在最优配对中。** 面积是 `min × 宽度`，不是 `max × 宽度`。直觉上"找最高的两条线"的思路在这里就失败了——这也是为什么排序或贪心地选最高的线行不通的原因。

## 代码（Golang）

```go
func maxArea(height []int) int {
	left, right := 0, len(height)-1
	best := 0

	for left < right {
		h := min(height[left], height[right])
		if area := h * (right - left); area > best {
			best = area
		}
		// 移动短板一侧的指针
		if height[left] < height[right] {
			left++
		} else {
			right--
		}
	}

	return best
}
```

几点关于这份实现的说明：

先算 `h := min(height[left], height[right])`，再用 `h * (right - left)` 计算面积，避免了在分支判断中重复写面积公式。`min` 在 Go 1.21+ 中是内置泛型函数，无须自行实现。

指针移动策略中，`height[left] < height[right]` 时移动 `left`，否则移动 `right`。当两边等高时移动哪个都不影响正确性——等高时无论移动哪边，当前配对的面积已被记录，两边各自向内探索即可。这里选择移动 `right` 只是因为 `else` 更简洁。

变量名 `best` 而非 `maxArea`（与函数名冲突）、`h` 而非 `minHeight`（作用域仅两行），符合 Go "作用域越小名字越短"的习惯。

## 易错点与实现陷阱

| 场景 | 陷阱 | 正确处理 |
|------|------|----------|
| 两边等高 | 只移动一边是否会漏解 | 不会，等高时移动任一边都安全 |
| 宽度为 1 | `min(h[0], h[1]) × 1` 是合法的最小容器 | 循环会自然覆盖到 |
| 误移动长板 | "移动高的那条线看看能不能找到更高的"——直觉上说得通但数学上不成立 | 移动长板不会增加 `min` 的上界，宽度还在减少，永远不会更优 |
| 面积公式用错 | 写成 `height[left] * (right - left)` 忘记取 `min` | 面积受限于短板，必须取 `min` |
| 循环条件 | 写成 `left <= right` 导致 `left == right` 时宽度为 0 | 应该是 `left < right` |

**最值得记住的一点**：这道题的双指针不是在"搜索"，而是在"排除"。每次移动短板，本质上是证明了"以短板为端点的所有剩余配对都不可能更优"，因此安全地跳过一整列候选。理解这个排除逻辑，比记住"移动短板"的操作本身重要得多。

## 可迁移的方法论

**对撞双指针 + 不可能性排除** 这个范式可以迁移到以下问题：

- **42. 接雨水**：同样涉及 `min` 操作和两端指针，但每个位置的贡献取决于"左边最高"和"右边最高"的较小值。核心仍是短板决定上界，但状态更复杂——需要动态维护左右前缀最大值。
- **167. 两数之和 II（已排序数组）**：对撞双指针的另一个经典场景。排除逻辑不同：当 `sum > target` 时移动右指针排除一整列过大的和，当 `sum < target` 时移动左指针排除一整列过小的和。
- **15. 三数之和**：外层枚举一个数，内层退化为两数之和的对撞双指针。迁移时保留"对撞+排除"的结构，增加去重逻辑。

迁移时需要注意的关键差异：本题的排除逻辑基于 `min` 函数的上界不变性，而两数之和类问题的排除逻辑基于有序性带来的单调性。结构相同（对撞双指针），但排除的数学依据不同。识别出"排除依据"是迁移成功的核心。
