# chroot — 隔离的起点

## 一个问题开始

假设你在一台 Linux 服务器上跑了两个客户的应用。客户 A 的应用能读到客户 B 的 `/etc/passwd`。这不是 bug，这是 Linux 的默认行为——所有进程共享同一个文件系统树。

**问题浮出水面：如何让一个进程认为 `/` 不是真正的 `/`？**

---

## 没有 chroot 之前

1979 年以前，Unix 系统里所有进程看到的文件系统是完全一样的。根目录就是根目录，没有任何歧义。

这意味着：
- 任何进程都能遍历整棵文件系统树
- 进程之间的文件隔离完全依赖权限控制（rwx）
- 一旦权限配置出错，就是全局暴露

权限控制回答的是"你有没有资格看"，而不是"这个东西在不在你的世界里"。这是两个本质不同的安全层次。

---

## chroot 做了什么

```
chroot(path)
```

一个系统调用。它做的事情极其简单：**把调用进程的根目录引用，从真正的 `/` 改为你指定的 `path`**。

之后，这个进程以及它的所有子进程，做路径解析时，`/` 指向的不再是系统的真实根目录，而是 `path`。

```
# 准备一个最小的文件系统
mkdir -p /tmp/myroot/{bin,lib,lib64}
cp /bin/bash /tmp/myroot/bin/
cp -L /lib/x86_64-linux-gnu/libtinfo.so.6 /tmp/myroot/lib/
cp -L /lib/x86_64-linux-gnu/libdl.so.2 /tmp/myroot/lib/
cp -L /lib/x86_64-linux-gnu/libc.so.6 /tmp/myroot/lib/
cp -L /lib64/ld-linux-x86-64.so.2 /tmp/myroot/lib64/

# 进入 chroot 环境
sudo chroot /tmp/myroot /bin/bash

# 现在在这个 shell 里，/ 就是 /tmp/myroot
# ls /  只能看到 bin lib lib64
```

注意你需要把 bash 依赖的动态链接库也复制进去。chroot 不会帮你处理依赖，它只改一个指针。

---

## 内核视角：到底改了什么

每个进程在内核中有一个 `fs_struct`，其中包含两个关键字段：

- **`root`**：路径解析时的根目录（dentry + vfsmount）
- **`pwd`**：当前工作目录

`chroot()` 系统调用修改的就是 `root` 字段。仅此而已。

这意味着：

- **`/proc` 不受影响**（除非你手动挂载）——进程仍然可以通过 procfs 看到系统信息
- **网络不受影响**——进程仍然共享主机的网络栈
- **PID 空间不受影响**——进程仍然能 `kill` 其他进程（只要有权限）
- **系统调用不受影响**——进程仍然能调用 `mount`、`reboot` 等

chroot 只骗了文件路径解析这一件事。其他所有内核接口都没有被隔离。

---

## 设计决策：为什么 chroot 如此"弱"

这不是设计缺陷，而是**设计意图**。

chroot 诞生于 1979 年（Version 7 Unix），Bill Joy 设计它的目的是**在编译和测试时提供一个干净的文件系统环境**。它从来不是一个安全机制。

关键设计决策：

### 为什么只改文件系统根，不做更多隔离？

1979 年的 Unix 哲学——**一个工具做一件事**。chroot 的职责就是改变路径解析的起点，其他隔离不是它的工作。

### 为什么 chroot 不是安全边界？

因为逃逸太容易了。一个 root 权限的进程可以：

```c
// 经典 chroot 逃逸
mkdir("escape");
chroot("escape");      // 创建一个新的更深的 chroot
// 此时 .. 就指向了原来的 chroot 外面
for (int i = 0; i < 100; i++) chdir("..");
chroot(".");           // 现在回到了真正的 /
```

原理：`chroot()` 改变了 `root`，但 `..` 的解析依赖于目录项的物理结构，不依赖进程的 `root` 字段。如果当前工作目录在 chroot 外（通过上面的技巧实现），就能一路 `..` 回到真正的根。

这不是 bug，而是 chroot 的设计边界——它明确不承诺安全隔离。

## 从 chroot 到容器：缺了什么

Docker 需要的是一个**让进程以为自己独占了一整台机器**的机制。chroot 只做到了文件系统维度的"幻觉"。

还缺：
- 进程树隔离（我看不到你的进程）→ **PID namespace**
- 网络隔离（我有自己的网卡和 IP）→ **Network namespace**（你很熟悉的领域）
- 用户隔离（我觉得自己是 root）→ **User namespace**
- 资源限制（你不能吃掉所有 CPU）→ **cgroup**
- 高效的文件系统层叠 → **overlayfs**

chroot 是这条路的第一步。它证明了一件事：**通过修改内核中的一个引用，就能改变进程的整个世界观**。

这个思路——不是限制进程的能力，而是**改变它感知到的现实**——正是 namespace 的核心哲学。

---

## 面试中的关键点

如果面试官问"Docker 是怎么实现隔离的"，大多数人会直接说 namespace。但如果你从 chroot 讲起，你展示的是一条**思想演进的线索**：

> "隔离的最早形态是 chroot——只改变文件系统的根。但很快人们发现，光骗文件路径不够，进程还能通过网络、PID、用户等维度看到外面的世界。于是 Linux 引入了 namespace，把这种'改变进程感知到的现实'的思路，推广到了六个维度。"

这比直接背 namespace 的类型列表有力得多。

## 留给你的问题

FreeBSD 做了一个叫 `jail` 的东西，比 chroot 强很多——它同时隔离了文件系统、网络和进程。Linux 没有走 jail 的路，而是选择了 namespace 这种"每个维度单独隔离"的方式。

**为什么？这两种设计哲学背后的根本分歧是什么？**

这个问题的答案会直接影响你理解 namespace 的方式。先想想，我们在下一篇里会回到这里。
