# LeetCode 5. 最长回文子串 —— 对称性、中心扩展与被忽视的奇偶统一

---

## 这道题在问什么

表面任务是：给定字符串 `s`（长度 ≤ 1000），找出其中最长的回文子串。回文是正着读和反着读一样的字符串，比如 `"aba"`、`"abba"`。

但如果你只想着"怎么检查一个子串是不是回文"，就会陷入枚举泥潭。这道题的底层结构其实是：**在一维序列上，利用回文的对称性质，快速确定每个可能的对称中心能向外扩展多远。** 回文的核心性质不是"首尾相同"，而是"围绕某个中心左右对称"。一旦把视角从"枚举子串然后判断"切换到"枚举中心然后扩展"，复杂度就从 O(n³) 降到 O(n²)。

## 为什么应该往"中心扩展"方向想

先看数据范围：`n ≤ 1000`，O(n²) 可以通过，O(n³) 也勉强能过但会很慢。这意味着我们至少需要一个 O(n²) 的方案。

再看回文的结构特征。回文有一个非常强的性质：**如果 `s[i..j]` 是回文，那么 `s[i+1..j-1]` 也一定是回文**（去掉最外层两个字符，内部仍然对称）。这是一个天然的递归/嵌套结构，暗示了两条路线——要么用动态规划（从短回文推长回文），要么用中心扩展（从中心往外逐步验证）。

两条路线的时间复杂度都是 O(n²)，但中心扩展在常数因子和空间上都更优。DP 需要 O(n²) 的额外空间来存状态表，中心扩展只需要 O(1)。在这道题的数据规模下，中心扩展是更自然、更直接的选择。

## 暴力思路与它的瓶颈

最朴素的思路是枚举所有 `(i, j)` 对，对每个子串 `s[i..j]` 检查是否为回文。枚举 O(n²)，检查 O(n)，总计 O(n³)。

瓶颈在于：每次检查回文时，我们没有利用"短回文和长回文之间的包含关系"。检查 `s[i..j]` 和检查 `s[i..j+2]`（假设 `s[i-1] == s[j+1]`）之间有大量重复比较。暴力解法把每个子串当作独立个体对待，完全浪费了回文的递归结构。

## 关键思维转折：从"枚举边界"到"枚举中心"

暴力解法的枚举维度是"子串的左右边界"。但回文不是由边界定义的——**回文是由对称中心定义的**。每个回文都唯一对应一个中心位置（奇数长度回文的中心是一个字符，偶数长度回文的中心是两个相邻字符之间的缝隙）。

这个视角切换带来的好处是：中心的个数是 O(n) 的（准确地说是 `2n - 1` 个：`n` 个字符中心 + `n-1` 个间隙中心），对于每个中心，向外扩展的过程最多 O(n) 步。总复杂度变成 O(n) × O(n) = O(n²)，且不需要额外空间。

这里有一个容易被忽视的细节：**奇数和偶数长度的回文需要分开处理**，因为它们的中心形态不同。`"aba"` 的中心是字符 `'b'`，而 `"abba"` 的中心是 `'b'` 和 `'b'` 之间的位置。如果只考虑单字符中心，`"abba"` 类型的回文会被完全遗漏。

最干净的处理方式是：对于每个位置 `i`，分别以 `(i, i)` 为中心做一次扩展（处理奇数长度），以 `(i, i+1)` 为中心做一次扩展（处理偶数长度），然后取两者中较长的结果。

## 为什么中心扩展是正确的

正确性来自两个方面：

**不会漏解。** 任何回文子串都有且仅有一个对称中心。如果是奇数长度，中心是某个字符 `s[i]`；如果是偶数长度，中心是某对相邻字符 `s[i]` 和 `s[i+1]`。我们枚举了所有 `n` 个单字符中心和所有 `n-1` 个双字符中心，因此每个回文子串的中心都被检查过。

**不会错判。** 扩展过程中，每一步都验证 `s[left] == s[right]`。如果相等则继续扩展，如果不等则停止。停止时，`[left+1, right-1]` 是以该中心为对称点的最长回文。这个过程只会返回真正的回文，不会多报。

**为什么扩展可以贪心地往外走？** 因为回文的嵌套性：如果 `s[left..right]` 不是回文（`s[left] != s[right]`），那么 `s[left-1..right+1]` 也不可能是以同一中心的回文。所以一旦扩展失败就可以立即停止，不需要跳过当前层继续尝试更外层。

## 复杂度的真实来源

**时间 O(n²)**：外层循环枚举 `2n - 1` 个中心，每个中心的扩展最多走到字符串边界。最坏情况是整个字符串本身就是回文（如 `"aaaa...a"`），此时中间位置的中心会扩展到 n/2 步。所有中心的扩展步数之和不超过 O(n²)——这不是均摊，而是直接由"中心数 × 最大扩展步数"上界得出的。

**空间 O(1)**：只需要维护当前最长回文的起始位置和长度，以及扩展过程中的两个指针。不需要任何表格或额外数据结构。这比 DP 方案的 O(n²) 空间优势明显。

对比一下 DP 方案的复杂度来源：`dp[i][j]` 表示 `s[i..j]` 是否为回文，状态数 O(n²)，每个状态转移 O(1)，总时间 O(n²)。时间复杂度相同，但空间代价多出 O(n²)，且缓存局部性更差（二维表的对角线遍历不利于 CPU 缓存预取）。

## 易错点与实现陷阱

| 场景 | 陷阱 | 正确处理 |
|------|------|----------|
| 偶数长度回文 | 只做奇数扩展，遗漏 `"abba"` 类型 | 每个位置做两次扩展：`(i, i)` 和 `(i, i+1)` |
| 返回子串而非长度 | 扩展结束后 `left` 和 `right` 已经越界一步 | 实际回文范围是 `[left+1, right-1]`，不是 `[left, right]` |
| 空串或单字符 | 忘记处理或逻辑错误 | 单字符本身就是长度为 1 的回文，空串返回 `""` |
| `"cbbd"` | 最长回文 `"bb"` 在中间，且是偶数长度 | 必须同时检查偶数中心才能找到 |
| 多个等长回文 | 题目要求返回其中一个即可 | 遇到更长的才更新，等长不更新 |

最关键也最容易忽略的思维转折：**想到"枚举中心"而不是"枚举边界"**。很多人卡在这道题上，不是因为不知道回文的定义，而是思维惯性地从两端枚举，没有意识到从中心出发才是回文问题最自然的分解方式。

## 代码（Golang）

```go
func longestPalindrome(s string) string {
	n := len(s)
	if n < 2 {
		return s
	}

	start, maxLen := 0, 1

	// 从中心 (l, r) 向外扩展，返回最长回文的长度
	expand := func(l, r int) {
		for l >= 0 && r < n && s[l] == s[r] {
			l--
			r++
		}
		// 循环结束时 [l+1, r-1] 是回文
		if length := r - l - 1; length > maxLen {
			start = l + 1
			maxLen = length
		}
	}

	for i := 0; i < n; i++ {
		expand(i, i)   // 奇数长度回文
		expand(i, i+1) // 偶数长度回文
	}

	return s[start : start+maxLen]
}
```

### 为什么这份实现是 Go 风格的

`expand` 用闭包而非独立函数，因为它需要访问外层的 `start`、`maxLen`、`s`、`n`。在 Go 中，当辅助逻辑只在一个函数内使用且需要修改外层变量时，闭包是最自然的选择——不需要传一堆指针参数，也不需要为此定义结构体。

切片表达式 `s[start : start+maxLen]` 是 Go 中取子串的惯用写法，零拷贝，直接返回底层字符串的一个视图。

`n < 2` 的提前返回是 Go 中处理边界的典型方式：在函数开头用 guard clause 排除退化情况，让后续主逻辑不用反复检查边界。这比在循环内部到处加 `if` 判断要干净得多。

变量命名上，`l`、`r`、`n`、`i` 这些在 Go 社区的算法代码中是完全可接受的——Go 推崇的命名原则是"作用域越小，名字越短"。`start` 和 `maxLen` 稍长，因为它们的生命周期跨越整个函数，需要更明确的语义。

## 可迁移的方法论

**中心扩展思路**直接适用于以下问题：

- **647. 回文子串**：不求最长，求回文子串的个数。同样枚举中心做扩展，但每次扩展成功计数 +1 而非更新最大值。
- **516. 最长回文子序列**：子序列而非子串，对称性仍在但连续性没了。中心扩展不再适用，需要切换到 DP（`dp[i][j]` 表示 `s[i..j]` 中最长回文子序列的长度）。这道题和第 5 题的对比，能帮助理解"子串"和"子序列"在算法选择上的根本差异。
- **214. 最短回文串**：在字符串前面添加字符使其成为回文。核心是找到从位置 0 开始的最长回文前缀，中心扩展可以作为子过程，但更优的做法是用 KMP 或 Manacher。

更广义地看，这道题训练的核心能力是**识别对称结构并选择正确的枚举维度**。当问题具有对称性时，枚举对称中心几乎总是比枚举边界更高效——这个原则在字符串、数组、甚至几何问题中反复出现。
