# 1. 两数之和 (Two Sum)

## 1. 30 秒面试回答

这题是**数组 + 哈希表查补数**。最优解是一遍扫描：`seen` 里始终保存当前下标左边已经出现过的数字及其下标。扫到 `nums[i]` 时，只要检查 `target-nums[i]` 是否已经在 `seen` 中；如果在，答案立刻成立。时间 O(n)，因为每个元素只做一次查询和一次插入；空间 O(n)，因为最坏要把所有前缀元素都存进哈希表。它成立的关键是：答案中的第二个数被扫描到时，第一个数一定已经在表里。

## 2. 我第一眼应该先想到什么

- **信号词**：`数组`、`和等于 target`、`返回下标`、`只需要一组答案`
- **为什么这些信号会把人引向哈希表**：题目不是要你统计多少组，也不是要连续区间，而是对每个数问一句"它缺的那个数之前出现过吗？"
- **第一次做最自然的暴力起点**：双重循环，枚举 `(i, j)`，检查 `nums[i]+nums[j] == target`
- **暴力真正慢在哪里**：对每个 `i`，你都把右边一大段 `j` 又扫一遍，本质上是在**重复寻找补数**。如果 `n=10^4`，这个重复扫描就是 O(n^2) 的瓶颈

## 3. 核心洞察

### 面试官想考什么

面试官想看你能不能把"找两数之和"翻译成"**找补数是否已出现**"，并自然地落到一遍哈希表。

### 面试官期望解 vs 快速稳妥解

这题两者**是同一个**，直接标成 **最优解**：

- **最优解**：一遍哈希表
- **面试策略一句话**：不要先讲排序双指针，直接讲"扫描当前数时，去哈希表里找补数"

### 最关键的不变量

`seen` 中只保存当前下标左侧元素的 `值 -> 下标` 映射。  
也就是说，当你处理 `nums[i]` 时：

- `seen` 里不会出现当前元素自己
- `seen[target-nums[i]]` 一旦存在，就一定对应另一个合法下标

### 为什么它是这题的命门

因为这题真正要回答的问题不是"哪两个数能凑成 target"，而是"**当前数的补数是否已经见过**"。一旦把问题改写成这个句子，哈希表就是顺手的结构。

### 为什么这样设计不会漏解

设答案是 `(i, j)` 且 `i < j`。当扫描到 `j` 时，`i` 已经被扫过，所以 `nums[i]` 一定已经在 `seen` 中；此时检查 `target-nums[j]`，必然命中 `nums[i]`。因此不会漏掉真正答案。

### 为什么容易误判成别的相邻题型

- **容易误判成排序 + 双指针**：双指针能找值，但原数组下标会被打乱，还要额外回映射，不是面试首选
- **容易误判成滑动窗口**：这题不是连续子数组，窗口没有单调推进依据
- **容易误判成"先存再查也行"**：这会把当前元素自己也放进表里，导致把同一个下标用两次

## 4. 最优解怎么一步步长出来

1. **暴力起点**  
   双重循环枚举所有二元组 `(i, j)`

2. **瓶颈**  
   对每个 `nums[i]`，都在右侧重新寻找一次 `target-nums[i]`

3. **观察到的规律**  
   对于当前数 `x`，你根本不关心右边所有人，只关心一个值：`target-x`

4. **如何利用规律进入最优解**  
   一边扫描数组，一边把已经看过的数放进哈希表；对当前数先查补数，再决定是否把自己存进去

### 最容易想错的思维岔路

**岔路**：先把 `nums[i]` 存进表，再去查 `target-nums[i]`

这会出错。例如：

- `nums = [3,2,4]`
- `target = 6`

如果 `i=0` 时你先存 `3 -> 0`，再查补数 `3`，会错误地得到 `[0,0]`，等于把同一个元素用了两次。

## 5. 手推一个关键样例

统一样例：`nums = [2,7,11,15], target = 9`

| 关键时刻 | 当前值 | 需要的补数 | seen | 结果 |
|---|---:|---:|---|---|
| 初始 | - | - | `{}` | 未找到 |
| 扫到 `i=0` | `2` | `7` | `{}` | 没找到补数 |
| 存入 `2` | `2` | `7` | `{2:0}` | 继续 |
| 扫到 `i=1` | `7` | `2` | `{2:0}` | 命中补数 |
| 返回答案 | `7` | `2` | `{2:0}` | 返回 `[0,1]` |

这里真正的转折只有一个：

- 扫到 `7` 的瞬间，不需要再看后面 `11`、`15`
- 因为 `7` 缺的就是 `2`
- 而 `2` 已经在 `seen` 里，所以答案在这一刻就闭合了

```text
          ^
          i=0
seen   : { 2 -> 0 }

Frame 4: 扫描 i=1, nums[i]=7

nums   : [ 2 ][ 7 ][ 11 ][ 15 ]
          [match]  ^
                   i=1
need   : 9 - 7 = 2
seen   : { 2 -> 0 }
ans    : [0, 1]

说明：补数 2 已经在 seen 中，对应下标 0，所以立刻返回。
```

## 8. Go 代码

```go
func twoSum(nums []int, target int) []int {
	idx := make(map[int]int, len(nums))

	for i, x := range nums {
		if j, ok := idx[target-x]; ok {
			return []int{j, i}
		}
		idx[x] = i
	}

	return nil
}
```

### 为什么主推这版

- 白板上最短
- 逻辑顺序就是面试表达顺序：**先查补数，再存自己**
- `make(map[int]int, len(nums))` 做了容量预估，符合 Go 惯用写法

## 9. 最容易写错的地方

1. **先存自己再查补数**  
   会把同一个下标用两次，这是本题第一高频 bug

2. **返回的是值，不是下标**  
   题目明确要的是 index，不是 `2` 和 `7`

3. **以为排序双指针更优雅**  
   排序后原下标丢失，还要额外映射，面试里反而更绕

4. **把这题写成滑动窗口**  
   这题不是连续区间，窗口移动没有依据

5. **面试官追问：为什么不会漏答案？**  
   你要能直接回答：当扫描到答案对里的第二个元素时，第一个元素一定已经在 `seen` 中

## 10. 相邻题迁移

### 1. 167. 两数之和 II - 输入有序数组

- **共用骨架**：本质仍然是在找两数凑成 target
- **关键不同**：数组有序，所以补数查找不再靠哈希，而是靠左右指针移动
- **该改哪一层**：只改"查补数"这层，从 `map` 查询改成 `left/right` 比较，不用从零重学"补数思维"

### 2. 15. 三数之和

- **共用骨架**：固定一个数后，剩下就是一个 `Two Sum`
- **关键不同**：要去重，而且不再是返回一组，而是返回所有组
- **该改哪一层**：保留"补数问题"的识别能力，只是在外面多套一层枚举 + 去重

### 3. 560. 和为 K 的子数组

- **共用骨架**：都是"当前量 + 哈希表查补数"
- **关键不同**：这里查的是 `前缀和差值`，不是单个元素值
- **该改哪一层**：把 `seen[value]` 换成 `cnt[prefixSum]`，核心思维仍然是"当前缺的东西之前出现过吗"
