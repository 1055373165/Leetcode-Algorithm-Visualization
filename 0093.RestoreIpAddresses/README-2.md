# 93. 复原 IP 地址（Restore IP Addresses）

## 0. 面试解题思路

这道题乍看像是字符串处理，但它真正考的是你能不能把"在一个数字串里插入三个点"这件事，抽象成一个带约束的搜索问题，并且把所有约束条件——段数、数值范围、前导零——干净利落地嵌入搜索框架中。面试官问到这道题的时候，我会这样说：

我把问题看作"依次切出 4 段"的递归过程。每一层递归从当前位置出发，尝试取 1 到 3 个字符作为一段 IP 数字。只有在满足三个条件时才递归进入下一层：长度合适、数值在 0 到 255 之间、没有前导零。当凑齐 4 段且字符串恰好用完时，就找到了一个合法 IP。由于每段最多 3 种长度选择、总共 4 段，搜索空间上界是 $3^4 = 81$，再加上剩余字符数的剪枝，实际分支远小于此。时间和空间复杂度都是常数级。

## 1. 问题本质与结构特征

题目要求在一个纯数字字符串中恰好插入三个点，将其分成四段，每段是 0 到 255 之间的整数且不允许前导零，返回所有合法的 IP 地址。

表面上是字符串切割，本质上是一个**段数固定、约束明确的组合搜索**问题。它的结构有两个显著特征：第一，段数固定为 4，这把搜索深度锁死了，意味着无论输入多长，搜索树的层数都是常数；第二，每段的长度范围极窄（1 到 3），这把每层的分支因子也锁死了。两者叠加的结果是整棵搜索树的规模是常数级的——这道题的难度不在算法效率，而在约束处理的完备性。

## 2. 为什么是回溯

n ≤ 20 这个范围看似宽松，但真正的约束来自 IP 地址的结构：4 段，每段 1-3 位，合法长度只有 4 到 12。超出这个范围直接无解。在这个范围内，搜索空间上界是 $3^3 = 27$ 种切法（3 个切割点，每个最多 3 种位置），加上约束过滤后实际分支更少。

题目要求"返回所有合法方案"，这排除了 DP 求最值或计数的路子——你必须把每一种具体方案都生成出来。贪心也不可能，因为不存在一个局部最优策略能保证覆盖所有合法 IP。

回溯搜索是自然且唯一的选择。这道题和 131. 分割回文串共享同一个回溯骨架——"从 start 位置出发，尝试合法前缀，递归处理剩余"——区别仅在于"合法"的定义和段数是否固定。

## 3. 暴力思路及其瓶颈

最直白的做法是用三重循环枚举三个切割点的位置，把字符串分成四段，然后逐一检查每段是否合法。三重循环的写法在 n ≤ 12 的规模下完全跑得动，时间上不是问题。

但它的瓶颈在结构而非速度。三重循环把"恰好分四段"这个需求硬编码成了固定的嵌套层数。如果第一段就不合法，你理论上应该跳过内层两重循环的所有迭代，但在嵌套循环中做这件事需要 break 加标签或者层层 continue，代码会变得冗长且容易出错。更重要的是，三重循环无法自然地推广——如果面试官追问"如果分成 k 段呢"，你就得重写整个循环结构。

回溯把每一层的切割逻辑抽象成递归调用，约束检查和剪枝天然嵌入递归结构中，代码简洁且可扩展。这不是一个性能优化，而是一个**表达能力的升级**。

## 4. 关键思维转折

**如果你没见过"固定段数的序列分割回溯"这个模式，你会卡在哪里？** 你会把这道题当成纯字符串处理，试图用循环和条件判断硬写，结果代码冗长、边界条件容易遗漏。转折在于意识到"插入三个点"等价于"依次切出四段"，而"依次切出"天然适合递归。

具体的优化观察：递归函数接收两个参数——当前起始位置 start 和已切出的段数 seg。在每一层，i 从 start 开始、最多走 3 步（因为每段最多 3 位数字），对每个候选子串 s[start..i] 做三重验证：长度在 1-3 之间、数值在 0-255 之间、没有前导零。只有三者都通过才递归。终止条件是 seg==4 且 start==len(s)。

还有一个容易忽视但效果显著的剪枝：在进入循环之前，先算一下剩余字符数 remaining = len(s) - start，以及还需要切出的段数 left = 4 - seg。如果 remaining < left（字符不够分）或 remaining > left*3（字符太多塞不下），直接返回。这个剪枝在最坏情况下不改变渐近复杂度（本来就是常数），但能有效减少实际递归调用次数。

## 5. 正确性论证

每层递归尝试长度 1、2、3 三种切法，覆盖了每段所有可能的长度。因此不会遗漏任何合法方案。

合法性验证包含三个条件：数值 ≤ 255 保证了段值合法；前导零检查拒绝了 "01"、"001" 这类违规格式；长度 ≤ 3 保证了不会出现 "0000" 被当作单段的情况。三个条件的逻辑覆盖是完整的——任何违反 IP 格式的段都会被拒绝。

终止条件要求 seg==4（恰好四段）且 start==len(s)（字符串完全消耗），两者缺一不可。只检查 seg==4 会收集到没有用完字符的方案，只检查 start==len(s) 会收集到段数不够的方案。双重检查保证了收集到的每一个方案都是完整且合法的。

搜索树中不同路径的切割位置序列一定不同——因为同一层内 i 是递增遍历的，不同层的 start 也是严格递增的——所以不会生成重复方案。

## 6. 复杂度的真实来源

**时间复杂度：常数级，严格上界 $O(3^4 \times 4) = O(324)$。**

搜索树的深度固定为 4（每层切出一段），每层的分支因子最多为 3（每段 1-3 位）。因此搜索树的节点数上界是 $\sum_{d=0}^{4} 3^d = 1 + 3 + 9 + 27 + 81 = 121$。每个节点内的操作——子串提取、数值转换、比较——都是 O(1) 到 O(3) 的常数。剩余字符数剪枝会砍掉大量分支，实际访问节点数通常只有几十个。最终拼接 IP 字符串的开销是 O(n)，但 n ≤ 12 所以也是常数。总时间不依赖输入规模，是严格的 O(1)。

**空间复杂度：O(1)（不计输出）。**

递归栈深度固定 4 层。存储当前四段的数组大小固定。没有哈希表、没有预处理表、没有辅助队列。输出空间取决于合法 IP 的数量，但在 n ≤ 12 的限制下，合法 IP 总数有上界（可以证明不超过几百个）。

## 7. 思路验证

**用例 1：s = "0000"** —— 专门测试前导零处理。

backtrack(0, 0)：切 "0"（length=1），val=0，无前导零，合法。进入 backtrack(1, 1)。切 "0"，合法，进入 backtrack(2, 2)。切 "0"，合法，进入 backtrack(3, 3)。切 "0"，合法，进入 backtrack(4, 4)：seg==4 且 start==4==len(s)，收集 "0.0.0.0"。

关键检验：回到 backtrack(0, 0)，尝试切 "00"（length=2）。sub[0]=='0' 且 length > 1，前导零，不合法。由于 val > 255 或前导零时应该 break（更长的子串同样不合法），直接终止循环。最终只输出 ["0.0.0.0"]。

如果没有前导零检查，"00" 会被接受为合法段，最终会生成 "0.0.00.0"、"0.00.0.0"、"00.0.0.0" 等非法 IP。

**用例 2：s = "25525511135"** —— 标准用例，体现完整搜索过程中的关键路径。

直接跟踪产生第二个答案 "255.255.111.35" 的路径：backtrack(0,0) 切 "255"（val=255 ≤ 255，合法）→ backtrack(3,1) 切 "255"（val=255，合法）→ backtrack(6,2) 切 "111"（val=111，合法）→ backtrack(9,3) 切 "35"（val=35，合法）→ backtrack(11,4)：seg==4，start==11==len(s)，收集。

这条路径上有个容易出错的判断：backtrack(6,2) 尝试切 "1"（合法）、"11"（合法）、"111"（合法）三种长度。只有切 "111" 时，剩余 "35" 恰好是 2 个字符给最后一段，才能凑齐 4 段用完字符串。切 "1" 时剩余 "11135" 有 5 个字符但只剩 1 段，5 > 3 触发剪枝。切 "11" 时剩余 "1135" 有 4 个字符、1 段，4 > 3，同样剪枝。这体现了剩余字符数剪枝的实际作用。

## 8. 易错点与边界

**前导零的判断用 break 而非 continue。** 如果 s[start..start+2] 有前导零（首位是 '0' 且长度 > 1），那么 s[start..start+3] 也必然有前导零。用 continue 跳过当前长度但继续尝试更长的，是一个逻辑错误。同理，val > 255 时更长的子串数值只会更大，也应该 break。这两个 break 是代码正确性的关键细节。

**字符串比较不能替代数值比较。** 一个常见错误是用 `target <= "255"` 做范围检查。Go 的字符串比较是字典序，"3" > "255" 为 true（因为 '3' > '2'），这会导致所有以 3-9 开头的合法段被错误拒绝。必须转成整数后比较。

**双重终止条件缺一不可。** `seg == 4` 确保恰好四段，`start == len(s)` 确保字符串用完。只有两者同时满足才是合法 IP。很多实现只检查其中一个，导致收集到段数不足或字符未用完的非法方案。

**单独的 "0" 是合法段。** 前导零规则拒绝的是 "00"、"01"、"001" 这类多位数以零开头的情况，而 "0" 本身是完全合法的 IP 段。判断条件必须是 `len(sub) > 1 && sub[0] == '0'`，而非 `sub[0] == '0'`。

## 9. 方法论迁移

这道题属于"固定段数的序列分割回溯"模式。它的框架可以直接迁移到以下题型：

**131. 分割回文串**是最直接的姊妹题。区别在于段数不固定（可以切成任意多段），约束从"数值范围+前导零"变成了"每段是回文"。迁移时去掉 seg 参数，终止条件从 `seg==4 && start==n` 简化为 `start==n`，isValid 函数替换为回文判断。回文判断如果频繁调用可以用 $O(n^2)$ 的 DP 表预处理到 O(1)，但 IP 地址题不需要这种预处理（每段最多 3 个字符，判断本身就是 O(1)）。

**842. 将数组拆分成斐波那契序列**更复杂：段数不固定，约束从静态的数值范围变成了动态的"前两段之和等于第三段"。回溯框架不变，但 isValid 需要知道 path 中最后两个元素的值，形成了段间依赖。这是"无依赖约束"到"有依赖约束"的进阶。

**468. 验证 IP 地址**则是反过来——给你一个已经带点的字符串，只需要验证格式是否合法。不需要搜索，纯解析。但验证逻辑（数值范围、前导零、段数）和本题的 isValid 完全一致，可以直接复用。

这组题的共同骨架是：递归函数以 start 为参数，循环尝试不同长度的前缀，用约束条件做剪枝，满足终止条件时收集答案。迁移时保留这个骨架，替换的是三个组件：段数限制（固定 vs 不固定）、合法性判断（数值 vs 回文 vs 字典 vs 斐波那契）、终止条件（段数+位置 vs 仅位置）。

## 代码

```go
func restoreIpAddresses(s string) []string {
	var ips, ans []string
	var dfs func(cur int)
	dfs = func(cur int) {
		if len(ips) == 4 {
			if cur == len(s) {
				ans = append(ans, strings.Join(ips, "."))
			}
			return
		}
		for i := cur; i < cur+3 && i < len(s); i++ {
			// 【核心】首位为 '0' 时只允许单字符 "0"，更长的必有前导零
			if i > cur && s[cur] == '0' {
				return
			}
			sub := s[cur : i+1]
			val, _ := strconv.Atoi(sub)
			if val > 255 {
				return // 更长的数值只会更大
			}
			ips = append(ips, sub)
			dfs(i + 1)
			ips = ips[:len(ips)-1]
		}
	}
	dfs(0)
	return ans
}
```
